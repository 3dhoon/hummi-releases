# Privacy Policy — Send to Hummi

**Last updated:** 2026-09-27

Send to Hummi is a Chrome extension that sends a user-selected YouTube tab or context-menu target to the locally installed Hummi desktop application.

## Information handled

- When the extension popup is opened, the extension reads the URL of the currently active tab to determine whether YouTube transfer is available.
- When the user explicitly clicks the send button, the extension passes the normalized YouTube URL, the selected media type (`audio` or `video`), and a request ID to the Hummi desktop application installed on the same computer. A YouTube Music playlist request may also contain the song-row recovery metadata described below.
- When the user chooses a context-menu action on a link or media element, the extension uses that target's link or source URL (not the current tab URL) and passes it to the Hummi desktop application after the same validation.
- On `music.youtube.com` only, a content script reads the video link, title, artist label, duration text, and album link from YouTube Music song rows. It keeps at most 300 validated row records in that page's extension memory so rows loaded while scrolling can be associated with a playlist request. When the user sends a playlist, the content script scrolls that page to the end for up to six seconds so rows below the fold are read too, then restores the previous scroll position; it does not click, play, or otherwise interact with the page. Matching row records are compressed into the local deep link. If the original video later fails in a way that means YouTube will not play that particular video id — deleted, private, region restricted, an unavailable format or player response, or a login requirement — the desktop app first tries the video id that YouTube Music itself showed for that row (YouTube Music substitutes a playable counterpart for an unavailable track, so this id can differ from the playlist's original id) and, only if that does not match the captured title and duration, may use the album link to ask YouTube for the album entry that matches the captured title and duration. The artist label is used only to rank several matching entries or when no duration is known.
- The `scripting` permission is used in one situation only: the user explicitly sends from the popup or the context menu while the active tab is a `music.youtube.com` page that was opened before the extension was installed, updated or reloaded, so its content script is absent. The extension then injects the same content script into that active tab under the `activeTab` grant and reads the song rows as described above. It never injects into other tabs or other sites.
- The last selected media type is stored with Chrome Storage Sync so the preference can be restored the next time the extension opens.
- The most recently right-clicked YouTube Music song-row record may be stored temporarily in Chrome Storage Session. It is ignored after one minute, replaced by the next song-row right-click in that tab, consumed when the context-menu request is handled, and otherwise removed when the browser session ends.
- The desktop application retains up to 100 recently opened or dismissed transfer request IDs in its own local webview storage to prevent replay after a screen reload. This deduplication record contains request IDs only, not source URLs or media contents, and is not sent to Chrome Sync or external services.
- If the user starts genre enrichment, the desktop application may send a track's title, artist, album, and duration to the public MusicBrainz Web Service to find recording candidates and genres. This is optional and uses a shared rate limit of at most one request per 1.1 seconds. The desktop application does not perform automatic post-download MusicBrainz enrichment.
- When the user starts a metadata search, they can select automatic, Bugs, or MusicBrainz as the source. The editor provides temporary search-title and search-artist fields, initially populated from the track metadata; changing them affects only the lookup and is not saved to the database or media file. The selected provider receives those search terms together with the current draft album and track duration. Automatic mode queries public Bugs pages first and contacts MusicBrainz only when the Bugs candidates do not contain a reasonably matching genre. Bugs lookup retrieves at most three candidate tracks serially with at least 2.5 seconds between requests. Login information, cookies, local file paths, listening history, ratings, and playlists are not sent.
- When the user asks the cover finder to search, the desktop application sends the enabled title and artist search fields, plus the current album and duration used for ranking, directly to public Bugs pages. Tracks in the same album group share one lookup. Search candidates remain temporary until the user confirms an automatic plan or manually selected covers. Applying a candidate downloads its image only from the supported public Bugs image hosts and stores the normalized cover locally.
- When the user creates video notes, the note text, timestamp, and video identity are stored locally in the Hummi database. Video notes are not uploaded to the developer or third-party services. If the user chooses to retain notes when deleting a video file, those notes remain local and can be removed from the archived-notes manager or reconnected when the same video is added again.

## Information not collected

Except for the limited YouTube Music song-row fields listed above, the extension does not read page text or HTML content. It does not read cookies, page `localStorage` or `sessionStorage`, password or form values, authorization headers, browsing history, personal communications, location data, or financial information. Chrome Storage Sync and Chrome Storage Session are used only as described above. The extension does not collect analytics, advertising identifiers, click statistics, or usage profiles.
MusicBrainz and Bugs requests do not include local file paths, playback counts, ratings, playlists, video notes, the rest of the library, YouTube cookies, or browser account information. The Hummi application does not upload listening history or a library index.

## Sharing and retention

The extension does not send data to the developer's servers, sell data, or share data with third parties. YouTube URLs, media type, request ID, and any YouTube Music row recovery metadata are transferred only to the locally installed Hummi application through the custom deep link; no local HTTP server is used. The desktop app contacts YouTube through yt-dlp for the requested preview or download and, only after an unavailable-media failure, may probe the counterpart video id captured for that row and query a validated YouTube Music album link included in that request. The desktop app's optional MusicBrainz and Bugs requests go directly to those services. Search candidates remain in the current editor session; only metadata or artwork the user explicitly saves is stored locally. Chrome preferences can be removed by clearing the extension's storage or uninstalling the extension.

In-page playlist recovery records are bounded to 300 and disappear when that content-script document is destroyed; they are not written to disk by the extension. The desktop application's request-ID history persists across screen reloads; older IDs are removed as new IDs exceed the 100-entry limit. That history contains request IDs only, not playlist recovery records. Clearing the desktop application's webview storage removes this history and its replay protection. Removing the Chrome extension does not clear the desktop application's storage.

The local transfer between the extension and the Hummi application is required to provide the extension's single purpose. The extension does not use or transfer user data for advertising, profiling, creditworthiness, lending, or any purpose unrelated to this functionality.
